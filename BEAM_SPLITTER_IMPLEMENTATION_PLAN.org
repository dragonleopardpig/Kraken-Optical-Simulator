* Beam Splitter Implementation Plan

** Status

As of 2026-05-01:

- Beam splitter UI is implemented.
- Deterministic child-branch spawning is implemented for surfaces carrying the
  =BeamSplitter= metadata dictionary with =split_mode = "Deterministic branches"=.
- =raykeeper= stores each child branch as a displayable ray path and records
  =BRANCH_ID=, =PARENT_BRANCH_ID=, =BRANCH_POWER=, =BRANCH_PHASE=,
  =BRANCH_LABEL=, and =SOURCE_RAY= metadata.
- The legacy =energy_probability= path remains a Monte Carlo branch chooser for
  ordinary coating experiments and for explicit =Monte Carlo coating split= mode.
- Finite plate splitters are modeled as two table rows:
  - coated front row: =surface = "Beam Splitter"=, substrate =Glass=, and plate
    =Thickness=
  - rear row: =surface = "Standard"=, =Glass = "AIR"=
  In KrakenOS local coordinates, rear =TiltX=0 models a parallel plate after a
  tilted front face; nonzero rear tilt models a wedge.

Relevant current code:

- UI surface menu: =KrakenOS/UI/layout_editor.py=
- 2D/3D scene generation: =KrakenOS/UI/scene_builder.py=
- surface data container: =KrakenOS/SurfClass.py=
- ray physics:
  - =KrakenOS/Physics.py=
  - =KrakenOS/PhysicsClass.py=
- core tracing / ray storage: =KrakenOS/KrakenSys.py=

** Goal

Add a new surface type =Beam Splitter= that can generate both transmitted and
reflected branches from one incident ray.

Target user behavior:

- user can insert =Beam Splitter= from the surface table
- 2D layout and 3D view show both branches
- each branch carries power / weight
- the user can choose which branch is the active branch for image-plane analyses
- save / load preserves beam-splitter settings

This should be implemented as a staged feature, not as one large patch.

** Current technical constraints

The current architecture assumes one outgoing ray per surface hit.

1. Physics layer
   - =snell_refraction_vector_physics.calculate()= returns one outgoing direction.
   - mirror behavior is represented by sign changes and a single reflected vector.
   - there is no return type for multiple child rays.

2. Tracing layer
   - =KrakenSys.py= advances one =ResVec= through surfaces.
   - hit data arrays store one sequence per ray launch.
   - path termination and distance accumulation assume one branch.

3. UI / scene layer
   - =RayPath3D= is already a good foundation for display, but it assumes one traced
     polyline per launched ray.
   - analyses such as Spot, PSF, MTF, field curvature, and distortion currently
     assume one image-forming branch.

The first engine change is now present. Remaining work is coherent Gaussian
state propagation and interference/ghost analysis on top of the branch records.

** Scope definition

*** Phase A scope: implemented

Implemented an *ideal splitting interface* with optional finite substrate
propagation when a rear surface is present.

Behavior:

- splitting interface controlled by =BeamSplitter=
- one transmitted branch
- one reflected branch
- user-controlled power split:
  - reflectance =R=
  - transmittance =T=
  - optional loss =L=
  - constraint: =R + T + L = 1=
- no polarization dependence in the first version
- no automatic ghost generation at ordinary rear surfaces; explicit additional
  splitter surfaces can be used for controlled ghost studies

This is enough to support:

- layout design
- folded path exploration
- branch visualization
- branch-by-branch spot tracing

*** Deferred scope: later phases

- wavelength-dependent coatings
- polarization-dependent splitting
- ghost path generation
- coherent interference between branches
- PSF / MTF composed from multiple simultaneous image-forming branches

** Proposed user model

Add a new surface type:

- =Beam Splitter=

Recommended first-version parameters per surface:

1. =surface=
   - =Beam Splitter=

2. =glass=
   - transmitted-side medium / substrate medium
   - default =AIR=

3. =rc=
   - same meaning as a normal surface for curved splitter experiments
   - default first use: plano splitter (=rc = 0=)

4. =diameter=
   - clear aperture of the splitter

5. =tilt_x, tilt_y, tilt_z, desp_x, desp_y, desp_z, axis_move=
   - same mechanical placement model as mirrors

6. New beam-splitter metadata
   - =split_mode=: =ideal= | =fresnel= | =plate= (start with =ideal= only)
   - =reflectance=: default =0.5=
   - =transmittance=: default =0.5=
   - =loss=: default =0.0=
   - =analysis_branch_policy=: =transmit= | =reflect= | =both-disabled=

The current table has no generic per-surface custom parameter fields, so these
splitter-specific settings should live in one of these places:

1. recommended:
   - surface-specific metadata stored in layout settings / side panel state
2. possible but less clean:
   - overload existing columns

Recommendation:

- keep the main table unchanged
- add a right-side *Beam Splitter* settings panel that appears when a
  beam-splitter row is selected

*** Scene representation

1. =RayPath3D=
   - add =branch_id=
   - add =parent_branch_id=
   - add =power=
   - add =branch_kind= (=primary=, =transmit=, =reflect=)

   - =RayNode=
   - stores a branch in the trace queue before conversion to display paths

3. Surface curve styling
   - beam splitter should have its own style hint
   - visually distinct from mirror and aperture

** Core tracing architecture change

This is the critical part.

The current tracer effectively does:

- propagate one ray
- hit one surface
- compute one output vector
- continue

Beam splitter requires:

- propagate one ray
- hit one surface
- compute up to two output vectors
  - transmitted
  - reflected
- push child rays into a work queue

*** Recommended branch-trace model

Use an explicit ray queue / breadth-first traversal.

Pseudo-structure:

1. launch initial rays
2. push them into =pending_branches=
3. pop one branch
4. trace until:
   - image
   - absorb
   - max surfaces
   - power below threshold
   - split depth limit
5. if current surface is normal:
   - continue as one branch
6. if current surface is beam splitter:
   - spawn:
     - transmitted child
     - reflected child
   - assign child powers
   - enqueue both

*** Required limits to prevent branch explosion

Add global controls:

- =max_split_depth=
- =max_total_branches=
- =min_branch_power=
- =analysis_active_branch_only=

Recommended defaults:

- =max_split_depth = 4=
- =max_total_branches = 256=
- =min_branch_power = 1e-3=

** Physics implementation plan

*** Phase 1 physics: ideal splitter

Add a helper that returns both branch solutions at one surface:

- transmitted branch:
  - same as existing Snell refraction
- reflected branch:
  - same as mirror reflection using the same local surface normal

Return structure should include:

- outgoing direction
- outgoing medium
- sign / propagation convention
- branch kind
- branch power

Recommended new helper:

- =compute_splitter_branches(...)=

This should reuse existing:

- =snell_refraction_vector_physics.calculate()=
- mirror/reflection logic already embedded in the same physics path
- =FresnelEnergy()= for future Fresnel mode

*** Phase 2 physics: Fresnel splitter

Once ideal mode is stable:

- derive =Rp, Rs, Tp, Ts= from current Fresnel functions
- convert to unpolarized branch powers
- optional later support separate S/P polarization state per ray

*** Phase 3 physics: plate splitter

Represent a physical plate as either:

1. one high-level beam splitter surface that internally generates:
   - front-face reflection
   - front-face transmission
   - back-face reflection
   - back-face transmission
2. or a macro object that expands to multiple actual surfaces

Recommendation:

- keep first implementation as thin ideal splitter
- revisit plate model after branch engine is stable

** Analysis plan

Analysis support should be staged.

*** Stage 1

Support only:

- layout view
- ray fan / spot-style branch visualization

Disable or warn for:

- PSF
- MTF
- wavefront-based metrics
- field curvature / distortion

unless the user explicitly chooses one active branch.

*** Stage 2

Allow analyses on a selected branch:

- =analysis_branch = transmit=
- =analysis_branch = reflect=

The engine should filter image-plane hits to that branch only.

*** Stage 3

Consider multi-branch analyses only after single-branch branch-filtered results are
stable. For most use cases, branch-filtered analysis is the correct behavior.

** Rendering plan

The scene pipeline is already close to what is needed.

Tasks:

1. Extend scene builder to recognize =Beam Splitter=
2. Add splitter surface style:
   - distinct color
   - optional dashed line or semi-transparent cyan/green
3. Extend ray rendering order:
   - central field still on top
   - within a field, higher-power branch on top
4. Add legend / status text:
   - branch count
   - active analysis branch
   - branch power thresholds

** 3D view plan

3D support should be limited initially to:

- show splitter surface geometry
- show both transmitted and reflected rays

Not needed in first version:

- coating visualization
- polarization vector display

If branch selection is synchronized with the table:

- selecting a splitter row can highlight both child branches

** Optimization plan

Do not make beam splitter a full optimization target in the first version.

First version:

- splitter geometry may be variable like normal rows
- branch ratio should be fixed, not optimized

Later:

- allow optimizing =reflectance=
- allow branch-weighted merit functions

This avoids mixing branching logic with the already complex optimizer path too early.

** Testing plan

*** Unit tests

1. Geometry
   - one ray at 45 degree onto plane splitter
   - reflected angle equals incident angle
   - transmitted direction matches Snell

2. Power bookkeeping
   - =R=0.5, =T=0.5, =L=0.0=
   - child powers sum to parent power

3. Queue limits
   - branch count clamps correctly
   - low-power branches terminate

4. Persistence
   - save / load preserves =beam_splitter= block

*** Integration tests

1. Single splitter
   - one incoming beam
   - two visible outgoing branches

2. Folded relay with splitter
   - one reflected fold branch
   - one straight-through branch

3. Two splitters in sequence
   - branch tree stays bounded
   - UI remains responsive

4. Analysis branch filter
   - transmitted branch reaches image
   - reflected branch can be selected separately

*** Regression tests

- existing Mirror behavior unchanged
- existing Aperture behavior unchanged
- old layout files load unchanged
- no performance regression for systems without beam splitters

** Phased implementation

*** Phase 0 - groundwork

Deliverables:

- plan document
- explicit non-goals
- code inventory of single-branch assumptions

*** Phase 1 - UI surface type and persistence

Deliverables:

- =Beam Splitter= appears in surface menu
- save / load support for splitter metadata
- placeholder drawing style

No branching yet. Layout can store the element.

*** Phase 2 - deterministic branch engine

Deliverables:

- ray queue / branch tree in tracing core
- ideal splitter spawns reflected + transmitted child rays
- branch IDs and powers stored in ray results

This is the main engine milestone.

*** Phase 3 - 2D/3D rendering

Deliverables:

- both branches visible in 2D
- both branches visible in 3D
- branch-aware picking / labels

*** Phase 4 - branch-filtered analysis

Deliverables:

- spot / ray-based analyses can choose a branch
- PSF / MTF remain disabled or explicitly branch-filtered

*** Phase 5 - Fresnel mode

Deliverables:

- optional =fresnel= splitter mode
- branch powers driven by Fresnel coefficients

*** Phase 6 - plate splitter and ghosts

Deliverables:

- optional physical plate model
- optional ghost path generation

** Risk assessment

High-risk areas:

1. Tracing core complexity
   - branching touches the deepest assumption in KrakenOS

2. Branch explosion
   - multiple splitters can grow ray count exponentially

3. Analysis ambiguity
   - many existing analyses assume one image branch

4. UI complexity
   - surface table must stay usable without adding many universal columns

Mitigations:

- implement ideal splitter first
- hard-limit branch depth and minimum power
- branch-filter analysis instead of trying to merge branches
- keep splitter settings in a side panel, not in extra table columns

** Recommended implementation order

If this work is resumed later, follow this order:

1. add plan file and keep it current
2. add =Beam Splitter= to UI surface enum and persistence
3. introduce branch data structures without touching all analyses
4. implement ideal splitter branch spawning
5. wire 2D rendering
6. wire 3D rendering
7. add branch-filtered spot/ray analyses
8. only then consider Fresnel / plate mode

** Minimum acceptable first release

The first usable release should satisfy all of:

- user can add a =Beam Splitter= row
- layout saves and reloads correctly
- one incident ray produces two visible branches
- branch power is shown
- branch limits prevent runaway growth
- existing mirror and lens layouts still work unchanged

If those are not all true, the feature is not ready to expose broadly.
