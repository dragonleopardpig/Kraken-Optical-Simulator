# Beam Splitter Phase 2 Plan

Date: 2026-05-01

Terminology update, 2026-05-04: the user-facing UI term is now `Path`. A path
is the editable physical ray segment between source/splitter/mirror/detector
nodes. This plan still contains older `arm` and `leg_id` implementation names
where they refer to saved metadata compatibility, and it still uses `branch`
where it refers to KrakenOS core trace metadata such as `BRANCH_PATH`.

## Status

Beam Splitter Phase 1 is implemented:

- The UI has a `Beam Splitter` surface type and saved `BeamSplitter` settings.
- `NsTrace` can spawn deterministic transmitted and reflected child paths.
- `raykeeper` records branch identity, parent branch, source ray identity,
  power, phase metadata, and branch labels.
- The finite-plate example uses a coated front face and a rear `AIR` face.
- The 2-D display can show both paths.

Phase 2 should make beam-splitter layouts useful for real optical design:

- ray bundles should be launched from the selected physical Source model
- irrelevant left-panel inputs should be hidden for source-driven systems
- optical components should be editable as elements assigned to separate
  transmitted/reflected paths
- analyses should be path-aware rather than assuming one image-forming path

## Core Design Constraint

Beam-splitter systems are non-sequential systems. The editable table must stop
acting like a strict optical-path sequence once a splitter creates multiple
paths.

KrakenOS non-sequential tracing chooses the next hit by geometry. Therefore:

- table order is an editing and grouping order, not necessarily propagation
  order
- the UI should describe scene objects, element groups, and path assignment
- branch paths are generated by ray tracing, not manually authored as row order
- moving an element up/down should move it within its logical path unless the
  user explicitly reassigns it

Do not create two unrelated sequential tables. One scene table plus path
metadata is easier to save, trace, inspect, and keep compatible with KrakenOS.

## Terminology

`Source`
: A physical launch description. It defines ray origins, directions, power,
  wavelength, and bundle sampling. In beam-splitter mode, this should be the
  launch authority.

`Element`
: A group of one or more table rows that behave as one optical component, for
  example a lens, plate beam splitter, mirror, detector, or imported catalog
  component.

`Path`
: A logical path segment generated by a splitter. Initial path roles:
  `Common`, `Transmit`, `Reflect`, and `Detector`.

`Branch`
: A traced ray child produced by the core. A branch has `branch_id`,
  `parent_branch_id`, `source_ray_id`, power, phase metadata, and hit records.

`Detector`
: A target plane/surface that receives one or more branch families. Detectors
  should be explicit elements, not only the final `Image` row.

## Phase 2 Goals

1. Make physical Source settings drive beam-splitter ray bundles.
2. Add path-aware element metadata and editing tools.
3. Add placement helpers for components in transmitted/reflected paths.
4. Add path filtering for plots and analysis.
5. Provide validation examples for common beam-splitter systems.

## Source-Driven Ray Bundles

Current UI has several source models, but many existing panels still come from
sequential lens design. In beam-splitter mode, source settings should become
authoritative.

Recommended behavior:

- If the selected source is physical, launch rays from `Source` position and
  direction, not from field/ray-height assumptions.
- Source models should include at least:
  - point source cone
  - disk source cone
  - collimated circular bundle
  - Gaussian beam bundle from waist or manufacturer diameter/divergence
  - weighted `SourceRnd.fun` angular distribution
- Source output should write per-ray metadata:
  - `source_ray_id`
  - source power weight
  - source wavelength
  - launch position
  - launch direction
- Branch children should inherit source metadata and multiply branch power by
  splitter/coating/bulk factors.

Panel behavior:

- Object mode should be hidden when the Source defines the launch.
- Ray height and field angle should be hidden when they do not participate in
  launch construction.
- Pupil controls should appear only when the source model uses pupil
  sampling.
- Gaussian source controls should hide finite-object fields that do not
  apply.
- The UI should keep hidden values in saved settings so users can switch
  workflows without losing previous inputs.

Display behavior:

- Show source position and source axis in 2-D and 3-D.
- Show traced paths with optional alpha/line width based on branch power.
- Allow coloring by field, source ray, trace path, wavelength, or path role.
- Provide a ray-count cap for preview and a separate analysis ray count.

## Path-Aware Editable Table

Keep one table. Add element-level metadata instead of adding many noisy columns.

Recommended element metadata:

```python
{
    "element_id": "E004",
    "element_name": "Transmit path collimator",
    "arm_role": "Transmit",
    "parent_splitter": "BS1",
    "branch_selector": "transmit",
    "arm_distance": 75.0,
    "local_decenter_y": 0.0,
    "local_decenter_x": 0.0,
    "local_tilt_x": 0.0,
    "local_tilt_y": 0.0,
    "local_tilt_z": 0.0,
}
```

Initial path roles:

| Path role | Meaning |
| --- | --- |
| `Common` | Before the first splitter or shared by all traced paths. |
| `Transmit` | Located on the transmitted path from a selected splitter. |
| `Reflect` | Located on the reflected path from a selected splitter. |
| `Return` | Optional role used later for folded/Michelson return paths. |
| `Detector` | Receives one or more branch families. |
| `Unassigned` | Existing imported rows before the user groups/assigns them. |

UI table rules:

- The first column continues to select a whole element group.
- Row background colors continue to mark element groups.
- Row selection should remain border-only so element colors stay visible.
- Path assignment should appear as a compact chip/badge in the element header or
  side panel, not as a mandatory wide table column.
- A path filter dropdown can show `All paths`, `Common`, `Transmit`, `Reflect`,
  `Detector`.
- Move Up/Down should move the selected element within its current path block by
  default.
- Reassigning an element to another path should be explicit through right-click
  or an Element Settings dialog.

Right-click actions:

- On splitter element:
  - `Create transmitted path`
  - `Create reflected path`
  - `Add detector to transmitted path`
  - `Add detector to reflected path`
  - `Show trace paths from this splitter`
- On element:
  - `Assign to Common path`
  - `Assign to Transmit path`
  - `Assign to Reflect path`
  - `Set path distance...`
  - `Flip element in path`
  - `Ungroup surfaces`
  - `Open Element Settings...`

## Path Placement Model

Phase 2 needs placement helpers so users do not manually calculate every
decenter/tilt for each path.

Each path should have a local coordinate frame:

- origin: splitter center or selected path anchor
- local `+Z`: nominal branch direction
- local `+Y`: display-plane transverse axis
- local `+X`: out-of-plane transverse axis

For a simple 45-degree plate:

- Common path nominal direction is the incoming source axis.
- Transmit path nominal direction is the transmitted branch direction after the
  rear plate face.
- Reflect path nominal direction is the reflected branch direction from the
  coated face.

When adding a component to a path:

1. User chooses component type and path.
2. User enters distance along the path.
3. UI computes global `Desp*`/`Tilt*` for the rows.
4. UI stores the path metadata so the component can be edited later in path
   coordinates.
5. KrakenOS still receives ordinary `surf` rows for tracing.

Important implementation point:

- The saved layout should keep both the final KrakenOS row values and the path
  metadata.
- If metadata is absent, old layouts still load and trace normally.
- If a user manually edits row pose fields, the UI should mark the path metadata
  as stale or offer `Update path coordinates from current pose`.

## Component Placement In Two Separate Paths

The table can be organized as readable blocks:

```text
Object / Source reference
Input collimator                 [Common]
50/50 plate beam splitter        [Common -> T/R]
Transmit path lens 1             [Transmit]
Transmit path detector           [Detector: Transmit]
Reflect path mirror              [Reflect]
Reflect path lens 1              [Reflect]
Reflect path detector            [Detector: Reflect]
Image / global fallback
```

This is not the propagation sequence. It is a scene object list grouped for
editing. Propagation is determined by geometry and branch tracing.

For simple users, provide path insertion commands:

- `Add lens to transmitted path at distance...`
- `Add mirror to reflected path at distance...`
- `Add detector to reflected path at distance...`
- `Add catalog component to transmitted path...`

For advanced users, keep manual row editing available.

## Path-Aware Analysis

Phase 2 should add a path selector that all downstream analyses can use.

Initial selector:

- `All paths`
- `Transmit path`
- `Reflect path`
- `Source ray N`
- `Branch ID N`
- `Detector element`

Analysis behavior:

- Spot diagram should be able to plot one detector/path at a time.
- Ray Inspector should show source ray, branch, parent branch, path label, power,
  phase metadata, and detector hit.
- Trace Path Inspector should group by source ray first, then trace path.
- Throughput report should sum branch powers by detector and path.
- CSV exports should include `arm_role`, `element_id`, `detector_id`, and
  `source_ray_id` where available.

Do not enable coherent interference plots until phase/OPL handling is validated.

## Phase 2 Implementation Slices

### P2.1 Source Authority

Status: in progress. Implemented so far:

- `Collimated disk source` launches an exact-count parallel bundle. Low ray
  counts use conservatively bounded, equal-spaced meridional samples for
  uniform 2-D preview gaps; larger counts use deterministic golden-angle disk
  filling.
- `Gaussian beam` launches an exact-count representative bundle derived from
  the current beam radius at the source plane, with the same low-count
  meridional and high-count disk-fill sampling rule.
- `Auto` trace mode resolves to `Non-Sequential Preview` when a physical source
  is used with a beam-splitter layout.
- `raykeeper` records launch metadata for every child branch:
  `SOURCE_RAY`, `SOURCE_XYZ`, `SOURCE_LMN`, `SOURCE_MODEL`, `SOURCE_POWER`,
  `SOURCE_WEIGHT`, and `SOURCE_WAVELENGTH`.
- Ray Inspector and CSV export expose source-ray and branch-power metadata.
- Deterministic splitter children are nudged off the hit surface after the real
  hit point is recorded, preventing immediate same-surface re-splitting.

- Make physical Source mode the launch authority in Non-Sequential Preview.
- Hide object/field/ray-height inputs that do not apply.
- Ensure Gaussian diameter/divergence source launches a representative bundle.
- Add source-ray metadata to all branch outputs.

Exit criteria:

- Point cone, collimated disk, and Gaussian source bundles fork correctly at a
  beam splitter.
- The UI clearly shows which controls are ignored.

### P2.2 Path Metadata And UI

Status: complete for the first path-metadata UI pass.

- Element metadata is saved in each row's `advanced["Element"]` dictionary
  with `element_id`, `element_name`, `arm_role`, `parent_splitter`,
  `branch_selector`, path distance, local decenter, and local tilt fields.
- `Element settings...` edits the metadata for one selected element.
- The right-click `Path assignment` submenu assigns selected elements to
  `Common`, `Transmit`, `Reflect`, `Return`, `Detector`, or clears the path.
- The first table column shows compact path badges (`C`, `T`, `R`, `D`, `RET`)
  on the first row of an assigned element without adding a new wide column.
- `Move Up`/`Move Down` uses path metadata: assigned elements move relative to
  the previous/next element in the same path; unassigned elements keep the
  original adjacent-block behavior.
- The table toolbar now exposes one visible `Path view` dropdown. It filters
  the table/plot to one path and preserves the table-to-KrakenOS surface index
  mapping.

Exit criteria:

- Users can group surfaces into elements and assign them to `Common`,
  `Transmit`, or `Reflect`.
- Move Up/Down operates within the selected path block.

### P2.3 Path Placement Helpers

Status: first detector-placement and path-labeling slices implemented.

- Beam-splitter row context menus now include:
  - `Add detector to transmitted path...`
  - `Add detector to reflected path...`
- The helper computes the selected splitter's world transform, derives the
  central transmitted/reflected branch direction, and inserts a `Standard`
  `AIR` detector plane before `Image`.
- The inserted detector row preserves global pose through row decenter/tilt and
  saves `Element` metadata with `arm_role=Detector`, `parent_splitter`,
  `branch_selector`, and `arm_distance`.
- The editable-table `Path view` dropdown discovers numbered path entries
  from saved metadata, e.g. `Path 1: Splitter transmit`.
- The 2-D layout plot labels discovered physical paths as `Path #` anchored to
  representative branch rays, falling back to component locations only when no
  traced branch ray is available.
- Core `NsTrace` branch results now carry a stable `branch_path` string such as
  `S1:BS1/transmit -> S4:BS2/reflect`. `raykeeper.BRANCH_PATH`, the scene
  bundle, Ray Inspector, Trace Path Inspector, and CSV exports expose it.
  This is the required identity layer for cascaded splitters and later
  Michelson/Mach-Zehnder recombination work.
- The Path dropdown and 2-D path labels now discover traced `BRANCH_PATH`
  records after `Update`. Saved element metadata is still honored for placed
  components, but pure traced splitter branches also appear as Path choices.
- The table toolbar `Path view` dropdown starts the Path Workbench workflow:
  `All paths` shows the full plot/table, while `Path #` filters the 2-D plot and
  editable table to common path surfaces plus that path's components and branch
  rays. The filtered table keeps an internal mapping back to real KrakenOS row
  indices.
- The documented tutorial workflow covers adding transmitted/reflected
  detectors, using `Path view`, and verifying path labels in Ray Inspector.

Remaining:

- Compute branch-local coordinate frames from splitter geometry.
- Generalize the placement dialog from detector planes to lens, mirror, and
  catalog components inserted into a path at a given distance.
- Add richer branch-local X/Y offset and tilt editing for placed components.
- Support tilted-source and multi-splitter path frames instead of assuming the
  nominal incoming source axis is global `+Z`.
- Expand the virtual path-workbench table with branch-local insertion helpers
  so newly added optics are physically placed in the selected path frame, not
  only tagged with selected-path metadata.
- Promote branch-local insertion and placement to use traced `branch_path`
  frames, so cascaded splitter paths can receive components without relying on
  row-order assumptions.
- Preserve both global row pose and path-local metadata.

Exit criteria:

- A user can create a two-path system without manually calculating decenter and
  tilt.

### P2.4 Path-Aware Analysis

Status: throughput report plus first path-filtered detector-analysis slices implemented.

- `Actions -> Path Throughput Report` groups traced leaf rays by output/path,
  branch selector code, branch path, and terminal detector/surface.
- The report has an initial path selector for all paths, output
  groups, branch codes, and terminal detector/surface groups.
- The report sums `branch_power * source_weight * source_power`, normalizes by
  unique launched source-ray input weight, and shows detector-hit count plus
  power-weighted optical path and geometric distance.
- The report supports Markdown copy and CSV export.
- The plot controls now expose an `Analysis path` selector populated from
  the same output/code/terminal identities.
- Selecting a non-`All paths` entry while using `Spot` or `RMS` plots traced
  non-sequential terminal hit points for that branch. Detector hits use
  detector-local coordinates when a surface transform is available, and RMS is
  power-weighted by branch/source power.
- Selecting a non-`All paths` entry while using `PSF` or `MTF` reuses the
  same detector terminal hit cloud to build a branch geometric PSF and
  detector-local geometric MTF.
- `Actions -> Export Path PSF CSV...` and `Actions -> Export Path MTF
  CSV...` write the same path-filtered PSF bins and geometric detector MTF
  curves used by the analysis panel.
- `DetMap` bins traced detector hits from a selected branch/terminal into a
  power-per-pixel detector map. It requires one selected terminal plane so
  local detector coordinates are not mixed across unrelated detectors.
- `Actions -> Export Detector Map CSV...` writes the same DetMap bins with
  branch filter, terminal, coordinate frame, bin bounds/centers, bin power,
  total power, and peak power.
- `CohDet` adds the first detector-pixel coherent sum from traced rays. It
  bins detector hits on one terminal plane and accumulates
  `sqrt(branch_power * source_weight * source_power) * exp(i phase)` using
  traced optical path length, wavelength, and deterministic `BRANCH_PHASE`.
- `Actions -> Export Coherent Detector CSV...` writes the same coherent
  detector grid with complex field real/imaginary components, coherent
  intensity, normalized intensity, incoherent power, wavelength, reference
  optical path, branch filter, terminal, and bin geometry.
- Plot Controls include `Detector bins` (`Auto` or 4-512) so DetMap and CohDet
  can use fixed detector sampling for repeatable plots and CSV regression
  checks.
- `python -m KrakenOS.UI.validate_branch_analysis` traces known
  detector-bearing layouts and validates detector terminals, DetMap, branch
  PSF, branch MTF, branch PSF/MTF CSV row builders, and CohDet outputs. Use
  `--json` for automation.
- `Deterministic coating table` is available in the beam-splitter settings
  dialog and direct API. It reads the row `Coating = [R, A, W, THETA]` table
  for branch powers, with fixed R/A fields as fallback.
- `Deterministic Fresnel P/S` is available in the beam-splitter settings
  dialog and direct API. It derives branch powers from KrakenOS core
  `RP`/`RS`/`TP`/`TS` Fresnel coefficients weighted by
  `polarization_p_fraction` (`1` pure P, `0` pure S, `0.5` equal P/S).
- deterministic splitter branches carry normalized `BRANCH_JONES_P`,
  `BRANCH_JONES_S`, and `BRANCH_POLARIZATION_XYZ` metadata; `CohDet` uses the
  global vector sum so orthogonal branch states do not interfere in one detector
  bin.
- Ray Inspector and Trace Path Inspector already expose branch/source metadata and CSV
  exports.

Remaining:

- Promote detector rows into a stronger detector element model for
  non-sequential analyses.
- Extend coherent detector analysis from exportable ray-bin summation to
  Gaussian/diffraction mode propagation.

Exit criteria:

- Transmit and reflect detector spots can be inspected independently.
- Reports state which path was analyzed.

- simple Mach-Zehnder geometry skeleton, ray-only, no interference claim

## Deferred To Later Phases

These should not block Phase 2:

- vector coating-stack behavior and birefringence beyond the current global
  branch polarization-vector metadata plus simple per-output splitter
  retardance controls
- multiple internal ghost reflections from both plate faces
- coherent recombination and Michelson fringe rendering
- full Gaussian q propagation through tilted non-sequential paths
- FFT/wave-optics propagation
- automatic optimization across both paths

## Michelson Readiness

Ray-only Michelson geometry is now available, but physically honest coherent
Michelson interferometry is still not complete.

Implemented now:

- `Common Optical Layout -> Michelson Interferometer (Ray Only)` builds an
  independent collimated source, a 45 degree deterministic 50/50 splitter, one
  return mirror in each path, and a second splitter encounter.
- The Source panel owns physical launch origin and direction through
  `Source X/Y/Z` and `Source L/M/N`; the `Object` row can be a reference plane
  instead of the ray launch source.
- The non-sequential branch queue skips the just-split surface once when a
  deterministic child branch is spawned, preventing same-surface self-hits on
  Michelson return/recombination paths.
- `KrakenOS/Examples/Examp_Michelson_Interferometer.py` prints branch path,
  power, phase, and optical path for direct API checks.

A full Michelson still requires additional validated pieces:

- regression checks for branch identity through more complex cascaded and
  nested splitter layouts;
- detector grouping for two recombined fields at the same output port;
- optical-path and phase accounting through the round trip, including splitter
  reflection/transmission phase conventions on both passes;
- coherent field summation/fringe rendering rather than drawing two unrelated
  ray bundles;
- Gaussian `q` propagation or wave-optics propagation through tilted,
  non-sequential paths before claiming laser-beam/interference accuracy.

Near-term acceptable examples:

- ray-only Mach-Zehnder skeleton with two splitters and two detectors;
- ray-only Michelson skeleton clearly labeled "no coherent recombination" and
  backed by branch-path diagnostics proving expected paths exist and power is
  bounded.

Do not label a preset as a real Michelson interferometer until the return-path
and coherent recombination checks pass.

## Key Risk

The main risk is mixing sequential assumptions into a non-sequential branch
system. The UI should explicitly communicate that the table is a scene/object
list once splitter paths exist. Path metadata and placement helpers should make
the system ergonomic, but the KrakenOS tracer should remain geometry-driven.
