* KrakenOS 3D Geometry Refactor Note

** Why this exists

The current UI mixes three concerns in one layer:

- optical computation
- display geometry generation
- viewer-specific rendering

That is workable for simple axial sketches, but it becomes fragile for:

- folded systems
- native off-axis surfaces
- external CAD overlays
- 2D section extraction from 3D geometry

DeepLens is useful here as a structural reference. Its main value is not STEP import, but the separation between lens model, generated geometry, and rendering.

** Current pain points

- The UI derives 2D and 3D geometry directly from plotting code.
- External CAD import is mesh-first, so mechanical alignment and sectioning are hard.
- 2D overlays are generated too late, after plotting decisions are already made.
- There is no stable geometry object representing:
  - optical surfaces
  - image plane / sensor plane
  - folded mirrors
  - external camera body

** Target architecture

Introduce an explicit geometry layer between KrakenOS optics and the UI.

1. *Optical model layer*
   - rows, materials, fields, aperture, wavelength
   - native KrakenOS system build

2. *Geometry build layer*
   - output explicit geometry objects in optical coordinates
   - independent of Matplotlib / PyVista
   - examples:
     - surface meridian polylines
     - lens body profiles
     - mirror planes
     - sensor plane
     - traced rays
     - external CAD shell
     - CAD section curves

3. *Render adapters*
   - 2D Matplotlib adapter
   - 3D PyVista adapter
   - export adapters:
     - PNG/JPG
     - STL/OBJ
     - STEP where CAD/BREP exists

** External CAD plan

For STEP or other mechanical camera models:

1. *CAD ingest*
   - load STEP with OpenCASCADE
   - detect solids, faces, cylinders, planes
   - cache metadata

2. *Mechanical cleanup*
   - keep dominant outer-body solids
   - optionally fuse them
   - suppress internal solids for display

3. *Registration model*
   - store per-model transform metadata:
     - rotation
     - forward axis
     - reference face
     - front / rear alignment rule
     - optional offsets

4. *Geometry outputs*
   - 3D display mesh
   - true YZ section curves for the 2D layout
   - optional silhouette curves for non-section views

5. *User controls*
   - select CAD model
   - show/hide CAD
   - adjust z/y offset
   - flip forward direction
   - choose reference face

** Why this is better

- 2D and 3D displays become consistent because they consume the same geometry objects.
- CAD alignment becomes a preprocessing problem, not a plotting hack.
- Saving display geometry becomes easier because geometry exists before rendering.
- Folded systems and native off-axis surfaces fit the same pipeline.

** Practical next steps

1. Move external CAD handling into a small helper module.
2. Add a serializable geometry dataclass set:
   - polyline2d
   - polyline3d
   - mesh3d
   - plane
   - label
3. Make the layout refresh produce a geometry bundle first.
4. Render the geometry bundle into:
   - 2D layout
   - 3D viewer
5. Add CAD registration presets in a data file rather than inline constants.

** Near-term implementation order

1. Stabilize reduced-shell STEP import and section extraction.
2. Add per-model alignment metadata and UI offsets.
3. Refactor current plotting helpers to consume intermediate geometry.
4. Unify folded preview and native off-axis preview under the same geometry API.
5. Add export of cleaned mechanical shell and optical geometry.
